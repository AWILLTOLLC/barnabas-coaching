Granting Jeff/Rambo gateway access — installer runbook

For the installer (Aaron/Dru). Customer in this run: Jeff; agent name: Rambo (per-customer — template docs stay generic, e.g. "Chief"). Target: bare Ubuntu 24.04 droplet, gateway as openclaw user on 127.0.0.1:18789.

Process split (agreed): the installer runs setup to a defined checkpoint first. Then the customer 1:1 call covers (a) OpenRouter account + credits + API key, and (b) granting Jeff access to the Control UI. Model-provider credentials are collected only on this call — never by email or chat. The Management Key stays in the operator's password manager; it never goes on the droplet.

1. Pre-flight (installer, before the call)

All commands on the droplet as root unless noted. Gateway CLI always runs as the openclaw user — running as root gives unauthorized: gateway token mismatch because root's config lacks the token.

  • Gateway active: systemctl is-active openclaw.service → active
  • Port listening: ss -tlnp | grep 18789
  • Persisted auth token present (pairing survives restarts): sudo -u openclaw openclaw config get gateway.auth.token returns a token, not empty
  • Model provider wired and proven: add-provider-keys.sh has been run and printed PROVIDER-PROOF-OK
  • Default model set to a model on the configured provider — a fresh install ships a placeholder that fails every turn. Example: 
    sudo -u openclaw openclaw config set agents.defaults.model.primary openrouter/z-ai/glm-5.3-flash
    (Use the provider-qualified ID — display names don't resolve in /model swaps either.)
  • Agent answers a turn: sudo -u openclaw openclaw agent --message "Reply with exactly: ALIVE-OK"
  • Workspace seeded: ls /home/openclaw/.openclaw/workspace/FULLINSTRUCTIONS.md exists; agent trigger message already sent

2. What the installer does (access grant)

Installer Goal: hand Jeff everything he needs to sign in from his own browser on the call.

  1. Verify gateway + workspace (pre-flight items above all green).
  2. Confirm the agent's owner status. Jeff is the owner: the onboarding conversation (FULLINSTRUCTIONS first boot) records him in USER.md. On the call, tell the agent: "This is Jeff, your new owner."
  3. Locate/generate the access info. The Control UI is served by the gateway itself at http://<host>:18789/ (docs: docs/web/control-ui.md). With a reverse proxy/TLS in front (see docs/gateway/stable-https-url.md), use that public URL instead. 
    # gateway token Jeff will paste into the Control UI sign-in
sudo -u openclaw openclaw config get gateway.auth.token
  4. Prepare pairing approval. A new browser connects → auth with the token → first connection may show disconnected (1008): pairing required. The preferred owner path is a short-lived single-use pairing link: 
    sudo -u openclaw openclaw dashboard   # prints a one-time pairing URL
    Alternatively, when Jeff's browser shows the pairing-required error, approve it on the host: 
    sudo -u openclaw openclaw devices list
sudo -u openclaw openclaw devices approve <requestId>
    Open any pairing link in Jeff's own browser so the durable admin credential lands there (a different browser profile can't inherit it).
  5. Confirm reachability. If Jeff accesses over SSH only, you'll open a tunnel together on the call: ssh -N -L 18789:127.0.0.1:18789 root@<DROPLET_IP>, then he browses http://127.0.0.1:18789/. If a public URL exists, verify it loads for him before the call ends.

3. What Jeff does (the 1:1 call)

Jeff with Installer assisting.

3a. OpenRouter key (screen-share, ~5 min)

  1. Jeff creates an OpenRouter account and adds credits (his card, his billing).
  2. Jeff generates an API key and shows it on the shared screen.
  3. Installer pastes it directly via the script — never email/chat, never into a transcript: 
    bash /root/add-provider-keys.sh   # hidden prompt; stages 0600, wires SecretRef, proves route, cleans up
    Wait for PROVIDER-PROOF-OK. If the default model isn't set yet, set it now (command in §1) and re-probe.

3b. First sign-in to the Control UI

  1. Jeff opens the gateway URL (public URL or SSH tunnel) in his own browser.
  2. On sign-in he pastes the gateway token you retrieved in §2.
  3. If pairing is required, you run the pairing command on the host and he opens the one-time link in the same browser.

3c. First message to Rambo

Jeff sends the trigger message:

Read FULLINSTRUCTIONS.md in your workspace and follow it.

What to expect (first-boot protocol): the agent introduces itself and asks for name, business, timezone, priorities; then writes USER.md, creates today's daily note, and updates the MEMORY-L0.md "Right now" header. Let Jeff answer the questions himself. Give it one or two real current priorities so the header isn't empty on day one.

4. Verification checklist (before you hang up)

  • Agent introduced itself and directed questions at Jeff (not the installer)
  • USER.md filled with Jeff's answers — no placeholders for known facts
  • memory/ exists with MEMORY-L0.md + today's daily note; "Right now" header populated
  • Agent correctly recalls one thing Jeff just told it (memory write works)
  • Control UI loads and connects from Jeff's own browser (not just yours)
  • Restart test (optional but recommended): systemctl restart openclaw.service → Jeff's browser reconnects without re-pairing (proves the persisted token)

5. Troubleshooting quick list

SymptomCause / fix
unauthorized: gateway token mismatch from CLI/TUIRan as root — root's config lacks the token. Always sudo -u openclaw openclaw … (e.g. sudo -u openclaw openclaw tui).
No route-compatible authentication source is configured for openai on every turnFresh install has no provider key AND/OR the default model is still the placeholder openai/gpt-5.6-sol. Run add-provider-keys.sh, then set the default to a model on the configured provider: sudo -u openclaw openclaw config set agents.defaults.model.primary openrouter/z-ai/glm-5.3-flash (provider-qualified ID).
Browser: disconnected (1008): pairing requiredNew device needs one-time approval: sudo -u openclaw openclaw devices list → devices approve <requestId>, or hand Jeff the openclaw dashboard one-time link opened in his browser.
Pairing breaks after gateway restartNo persisted gateway.auth.token — the gateway minted a runtime token that can't be recovered. Re-run first-run.sh (persists the token) or openclaw doctor --generate-gateway-token before the unit exists; restart.
openclaw doctor --fix refuses: "service ownership could not be verified"Expected once a systemd unit exists. Onboarding must precede unit creation. Verify health via systemctl is-active + ss -tlnp | grep 18789 instead.
Setup script aborts with systemctl is-active = activatingGateway mid-boot during set -e. Use the retry loop (first-run.sh has it); don't re-add bare is-active checks.
Delivery warnings on cron jobsCron fires but channel/delivery isn't configured for the target — expected until channels are set up with the customer (Step 5 of SETUP-WALKTHROUGH). Note and move on.
